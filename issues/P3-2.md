# P3-2 — `HttpException::VERSION` has zero references, and the base class …

    deleting it would be a public-API/breaking change, and `tests/HttpExceptionTest.php:91-94` already

    the family is a convention, not a defect — I will not touch it.
  - **Status code — reproduced here; the fix is a decision only you own.** Probe through this module's
    own `vendor/autoload.php`: `new HttpException(0)`, `(999)`, `(-1)`, `(600)` and `(418)` are all
    accepted and `getCode()`/`getStatusCode()` echo the value (`src/HttpException.php:19-26`). A range
    check is a **behaviour change**, so per the interaction contract I am asking instead of choosing.
  - The fork, with the cost of each side:
    - **Option A — validate in the base constructor** (RFC 9110 range, `100–599`). Behaviour change:
      code that today builds a placeholder / `0`-coded exception would start throwing; the README's
      `418` example stays valid (418 ∈ range). Needs a decision on the error type
      (`InvalidArgumentException` vs. a new class), a regression test for each rejected code, and both
      README halves plus the `@param` note updated. Buys: an invalid code fails fast at construction.
    - **Option B — keep permissive, document it explicitly** (e.g. `@param int $statusCode HTTP status
      code; not range-validated — the framework validates before sending`). No behaviour change, no BC
      risk, and it keeps the class a pure carrier, consistent with `README.md`'s "framework-agnostic …
      the framework decides how to send them". Cost: a nonsense code is only caught when the response
      is sent.
  - My opinion: **Option B.** The class carries data and the README already documents a custom code;
    validation belongs to the sender. I will not touch `src/HttpException.php` until you choose.
